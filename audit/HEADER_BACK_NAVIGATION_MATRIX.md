## Corrections vs the earlier draft (this pass closed the flagged gaps)

1. **Nic.tsx back target — confirmed BROKEN, not just "likely dead/stale."** Previous draft (row for `/onboarding/nic`) said "possible broken back target... likely dead/stale link." Verified: `Nic.tsx:28` calls `navigate('/welcome/otp')`. Grepping all of `App.tsx:184-235` for registered paths shows no `/welcome/otp` route exists (only `/onboarding/otp` and `/welcome` are registered — `App.tsx:187-206`). React Router's catch-all (`App.tsx:233`, `<Route path="*" element={<Navigate to="/" replace />} />`) therefore fires, silently bouncing the user to Home instead of back to the OTP screen. The same bad target is used forward by `Join.tsx:22` (`navigate('/welcome/otp', { state: { phone: full } })`), so this is a pre-existing two-sided bug in the legacy onboarding flow, not something the header refactor introduces. `Otp.tsx:31` by contrast correctly targets the registered `/welcome` route.

2. **Profile.tsx root header back button — confirmed real risk, mechanism now precise.** Previous draft didn't analyze this. Verified: `Profile.tsx:79-86` renders a hero-header back button (`pf-icon-btn`) wired to `navigate(-1)` unconditionally, with no root-tab guard. `BottomNav.tsx:34-39` lists `/profile` as a bottom-nav tab, and `App.tsx:176-180` shows `RequireAuth` can land a fresh session directly on whatever route follows login — if Profile is opened as the first screen after auth (e.g., a future deep-link to `/profile`, or a session where history was reset), `navigate(-1)` has no prior in-app entry to return to and either does nothing (SPA history stack empty) or exits to whatever was in the browser's session history before the app loaded (another site, or nothing on a fresh PWA launch). This is the same class of bug as Gallery's missing back control, just inverted (Profile has a back button that can go to a wrong/empty target; Gallery has no back button at all).

3. **Gallery.tsx — confirmed NO header/back control exists at all** (previous draft flagged this as "cannot confirm, flag for follow-up" — now resolved). Verified full file read (`Gallery.tsx:1-108`): the header block at `Gallery.tsx:66-75` is a plain `<div>` with an icon tile and title/subtitle text — no back button, no `ScreenHeader`, no `onClick` handler anywhere in the header. The only interactive elements on the whole screen are the category filter chips (`Gallery.tsx:78-82`) and the album tiles themselves. `/gallery` is reachable from Community-tab navigation (`BottomNav.tsx:32` matches `/gallery` under the Community tab) but once there, the only way back is the bottom nav itself or the browser/hardware back gesture — there is no in-page affordance. This is a harder gap than "inconsistent back button," it is "missing back button."

4. **Language.tsx — resolved the "possible double back-handling" flag; it is NOT double-handling, it's two different triggers for two different purposes, but still worth standardizing.** Full file read (`Language.tsx:1-43`) shows exactly two navigation-adjacent calls:
   - `Language.tsx:23` — `<ScreenHeader titleTa={...} titleEn="Choose language" />` passes no `onBack`, so it falls through to `ScreenHeader`'s own default (`ScreenHeader.tsx:15`, `onBack ?? (() => navigate(-1))`) — this is the header's back chevron, standard history-back.
   - `Language.tsx:18` — inside the `choose(l)` handler (fired when the user taps a language row, not a back button), after `await setLang.mutateAsync(l)` and `await i18n.changeLanguage(l)`, the code calls `navigate(-1)` to close the Language screen and return to wherever it was opened from (Profile's menu row or Home's language chip).
   So there are two distinct `navigate(-1)` call sites, but they are not competing/redundant — one is the header back button, the other is "save and return" after selecting a language. Both target the same action (`navigate(-1)`) which is consistent, but it means Language has an implicit "any tap on a row = commit + exit" pattern with no visible Save/Done button — worth flagging as a UX consistency item (not a navigation bug) in the design spec.

5. **BackChip — confirmed usages and inconsistency with `ScreenHeader`'s back button, not previously documented with line citations.** `BackChip` is defined once at `parts.tsx:375-386` and used in exactly two places: `SignUp.tsx:65` (`<BackChip onClick={back} />`, where `back` is a local function at `SignUp.tsx:36-39` that pops the in-screen step wizard back to step 0 before actually navigating to `/login`) and `Forgot.tsx:30` (`<BackChip onClick={() => navigate('/login')} />`, a hardcoded target, not `navigate(-1)`). It is NOT used anywhere in `onboarding/*.tsx` — those screens (`Nic.tsx`, `Otp.tsx`) use `ScreenHeader` instead, so "BackChip in onboarding" from the original task framing does not apply; BackChip is auth-only (`SignUp`, `Forgot`). Geometry differs from `ScreenHeader`'s back button: `BackChip` is 44×44 but pill-shaped with a visible 1px border and drop shadow using `authC` tokens (`parts.tsx:381`), `ScreenHeader`'s is 44×44 but borderless/transparent using `c` tokens (`ScreenHeader.tsx:31`) — same hit-target size, different visual treatment and a separate color-token namespace (`authC` vs `c`).

6. **ReportNew.tsx / ReportDetail.tsx — confirmed ORPHANED, not "likely reached via in-screen state" as previously hedged.** Grepping all of `app/src` for `ReportNew|ReportDetail` returns exactly two matches, both the components' own `export function` declarations (`ReportNew.tsx:13`, `ReportDetail.tsx:9`) — zero import statements anywhere else in the codebase, and `App.tsx:184-235`'s full route table has no `/report/new`, `/reports/new`, `/report/:id`, `/reports/:id` or similar path. These two files are dead code: not routed, not imported, not rendered by `Reports.tsx` (which implements its own inline create-form and list — `Reports.tsx:100-315` — duplicating whatever `ReportNew`/`ReportDetail` were meant to do). Any back button inside them is moot since nothing currently mounts them.

7. **Reports.tsx FAB entry point — now identified precisely.** `BottomNav.tsx:21-27` already wires the center FAB tab to `to: '/reports'`. `Reports.tsx:50` initializes `const [tab, setTab] = useState<0 | 1>(0)`, i.e. tab 0 (`ReportForm`, the create flow) is the default view on a fresh navigation to `/reports`. So the center FAB's existing behavior — `navigate('/reports')` — already lands the user on the create-report form with zero additional wiring. No new route or handler is needed for a future FAB; it should keep calling the same `/reports` route the bottom nav already uses, not a new modal or a route to `ReportNew.tsx` (which is unrouted dead code per #6).

8. **Back-gesture / deep-link handling — net new finding, not in earlier draft.** Grepped `app/src` for `popstate|history\.|beforeunload` — zero matches anywhere in the app source. There is no custom back-gesture interception, no `beforeunload` guard, and no manual `history` manipulation anywhere in the app: all back/forward behavior is whatever `react-router-dom`'s `BrowserRouter`/history give for free, and the Android/browser hardware-back gesture is not special-cased at all (so it behaves exactly like `navigate(-1)` from a header, with the same risks noted in #2 for any screen reachable as a root). Deep-link / hard-refresh behavior on a nested route (e.g. loading `/reports` directly) depends on the dev/prod server serving `index.html` for unknown paths; `vite.config.ts:48-58` only configures the dev server's `/api` proxy and does not show an SPA fallback — this needs the production server config (outside `app/src`, likely in `server/` or a hosting config) to confirm hard-refresh-on-nested-route doesn't 404, which is out of this pass's scope (audit covers `app/`, not `server/` or deploy config in depth).
